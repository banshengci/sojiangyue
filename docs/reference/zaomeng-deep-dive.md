# 造梦（zaomeng）深度调研

> 调研对象：`github.com/wkbin/zaomeng`，本地副本 `D:\xiangmu\ref\zaomeng`（浅克隆，2026-10-18）
> 调研方式：只读，读文档、提示词、契约与模块结构；**未复制任何代码或提示词文本**
> 结论先行：造梦强在**人物模型的分层**与**对话的质量闭环**，弱在"读"（它没有阅读器）。我们的短板正好相反。

## 0. 结论先行

三件最值得学的东西，按性价比排序：

1. **人物分 8 层，只有 MEMORY 允许运行时写入**——它用结构解决了"人物会演进"与"设定不能漂"的矛盾。我们现在是一张扁平卡，两边都做不到。
2. **知识边界（knowledge boundary）+ 知识台账（knowledge ledger）**——每条事实登记"谁知道"，越权发言由提示词+台账双重约束。我们只有"锁定事实"，没有"谁知道"。
3. **一次生成 + 异步一致性审校 + 按问题重写同一轮**——把质量检查从"一次赌对"变成"生成→体检→返工"。我们现在是一次成型，错了只能整轮重来。

另有一条**授权红线**：造梦是 **AGPL-3.0**，松江阅是 **MIT**。
把 AGPL 代码并进 MIT 项目会让整个项目被传染成 AGPL。所以"不抄代码"不只是偏好，是硬约束；
可以借鉴的是**机制、分层、字段设计与提示词策略**（这些属于思想，不受版权保护），
但**不要复制提示词原文**——提示词是受版权保护的表达，重写。

## 2. 架构

```
Compose UI → ViewModel → Repository → localhost HTTP/SSE → Ktor Routes → Services
                                                              ├── StorageService → Room
                                                              ├── PromptLoader
                                                              ├── LlmClient（OpenAI 兼容）
                                                              └── Plugin Host
```

四个值得记的点：

1. **同进程内嵌 HTTP**：UI 走本地 HTTP/SSE 而非直接调 Service。好处是"断线重连、幂等、流式"都在同一套协议里解决；代价是复杂度。
2. **双存储**：`documents` 表存 JSON/Markdown 文档，领域表存索引/分页。文档是真相，领域表是可查视图。
3. **transcript 有界**：会话 manifest 只存近期若干条，超出部分**成批归档**到 archive 文档，manifest 只留 `transcript_start` / `transcript_count`。生成路径永不读全量历史。
4. **原文不整份上模型**：本地建检索结构，每轮只取少量摘录注入。IO 成本与 token 成本分离。

> 对照我们：对话历史是全量读进内存再截断（`maxHistoryMessages = 24`），记忆用"折叠摘要"。
> 我们更简单，但长会话的 token 与页码会随轮数漂；它用"有界 manifest + 归档"把这件事变成常数。

## 3. 人物模型：8 层 persona bundle（最重要的发现）

人物不是一张卡，而是一组分层文件，每层有明确职责与**写策略**：

| 层 | 职责 | 必填 | 写策略 |
|---|---|---|---|
| `SOUL` | 核心价值、世界观、底线；立场/禁忌/拒绝方式 | 是 | 仅人工 |
| `GOALS` | 长期驱动、未完成的欲望、决策优先级 | 否 | 仅人工 |
| `STYLE` | 招牌措辞、节奏、表层情绪、**代表句** | 否 | 仅人工 |
| `TRAUMA` | 痛点、创伤、禁忌触发、绝不做的事 | 否 | 仅人工 |
| `IDENTITY` | 出身、经历、习惯、情绪画像 | 是 | 仅人工 |
| `AGENTS` | 运行时行为规则：**何时开口、何时沉默、群里怎么接话** | 是 | 仅人工 |
| `RELATIONS` | 对具体对象的信任/好感/称呼/摩擦点 | 否 | 仅人工 |
| `MEMORY` | 稳定备注 + **运行时写回**（用户纠正、长期约束） | 是 | **运行时追加** |

**这就是"人物演进"的正解**：只有 `MEMORY` 一层可被运行时写回，其余七层永远只读。
于是"角色聊得越久越不一样"与"设定不能被聊坏"同时成立——不是靠提示词小心，是靠**结构禁止**。

我们现在的 `CharacterCard` 是扁平的（personality / background / motivation / appearance / description），
所有东西混在一张卡里；一旦允许写回，就分不清哪部分是"书里写的"、哪部分是"聊出来的"。

> 可落地做法（不需照抄字段）：把现有的"蒸馏产物"标记为只读，另开一张 **对局记忆表**（按会话或按人物累积），
> 注入时二者分区呈现，且**永不回写人物卡**。

## 4. 会话状态：canonical `state` + 稳定性分级

`session.state` 是唯一真相，固定七个块：

```json
{ "version": 1, "scene": {}, "presence": {}, "progression": {},
  "relations": {}, "characters": {}, "signals": {}, "memory": {} }
```

| 块 | 内容 |
|---|---|
| `scene` | 地点、时间提示、氛围、当前推进说明 |
| `presence` | 谁在场、谁离场 |
| `progression` | 这一拍是否成熟、是否该转场、世界张力 |
| `relations` | **基线关系矩阵 + 本局增量**（分开存） |
| `characters` | 会话级角色快照（当前状态，非永久档案） |
| `signals` | 最近事件信号 |
| `memory` | 会话摘要与压缩态 |

三个设计细节：

1. **关系分两层**：`relations.matrix`（基线，来自书）与 `relations.delta`（本局变化）。快照与增量都不回写人物卡。
2. **稳定性分级**：每个子块标 `stable` / `evolving` / `experimental`，并写清"能不能删字段、要不要兼容期"。这是给未来的自己留的说明书。
3. **投影视图**：`scene_progress` / `relation_delta` / `character_snapshots` 全部是 `state` 的派生视图，前端只消费视图。

> 对照我们：`GameplaySession` 已有 `stats` / `memberStats` / `phaseIndex` / `log` / `secret`，
> 但**没有"基线 vs 本局增量"的区分**，也没有稳定性分级。玩法包一旦多了，字段兼容会变成事故源。

## 5. 对话引擎

### 5.1 输出协议：NDJSON

每行一个完整对象，必填 `speaker` + `message`，可选 `inner_thought`。
好处：可以**逐行增量投影**——`speaker` 完整、`message` 开始到达就能上屏，不必等整份 JSON。
配套硬规则：

- 禁止代码围栏（实测某些模型爱包 ```json，且同行还会破坏解析）；
- **同一角色不得连续发言**（连续内容必须合并在一个对象里）；
- 解析失败重试一次，`maxTokens` 翻倍 + 换一套"重试专用"提示词。

### 5.2 谁该说话：SPEAKER_PLAN

每轮先算一个"介入优先级"（`recommended_speakers`），提示词要求：
优先参考它，但角色与当前动作无关时可以少说或不说；离场角色、用户控制的角色不得越权发言。

另有 `rules/speaker_rules.md` 提供**确定性信号**：疑问词表（是否/要不要/该不该）、
战事词表、休憩词表、关切词表，以及"性格 → 优先维度"的映射表（谨慎→智慧、敏感→善良…）。
不是让模型猜谁该说话，而是先给一个可解释的路由建议。

### 5.3 知识边界：谁**知道**什么

这是它比我们强的地方。每条事实可带 `holders`（持有人名单）：

> `KNOWLEDGE_BOUNDARY` 中每条 fact 只允许 holders 中的角色知晓。未列入者不得提及、暗示或据此行动。

配合 `knowledge_ledger`（服务端维护的"谁知道什么"台账，`updateKnowledgeLedger`），
**越权知情**从"提示词提醒"变成"数据约束 + 台账校验"。

### 5.4 原文证据的门控

检索出的原作片段带 `allowed_characters` 与 `visibility`（如 `uncertain`）：

- 角色只能使用包含自己名字的片段；
- `visibility=uncertain` 的片段只允许旁白组织场景，角色不得当作自己知道的事实；
- 原文证据**优先于模型预训练记忆**，且不得在回复中引用出处。

### 5.5 质量闭环（我们完全没有）

```
生成 → 结构校验 → 提交 → 后台一致性审校 → 有 issues 则按问题重写同一轮
```

审校器只查四类语义漂移：

| code | 含义 |
|---|---|
| `semantic_voice_drift` | 口吻不像人物 |
| `semantic_motivation_drift` | 动机/决策逻辑突变 |
| `semantic_relationship_drift` | 态度与当前关系冲突 |
| `semantic_knowledge_drift` | 用了不该知道的信息 |

每条 issue 必须带**逐字摘录的证据**（2–40 字）。重写时用 `CORRECTION_CONTEXT` 逐项消除 issues，
并明确要求"保留已成立的场景事实，不要解释修正过程，也不得凭空新增事件"。

> 这条对我们最有用：现在角色一旦 OOC，用户只能点"重新生成"，抽一次新的运气。

## 6. 三个高级动作

### 6.1 导演（Director）

不是"选五个动作"，而是**让模型把导演目标拆成 2–4 个可立即演绎的下一拍方案**，每个方案含：

`title`（4–10 字）/ `focus` / `beat`（下一拍具体发生什么）/ `direction`（给代写模型的写作指令）/ `expected_effect` / `risk`

第四面墙模式额外要求 `resistance`（哪些角色会拒绝及理由）与 `price`（角色提出的交换条件）——
**允许角色跟作者讨价还价**，而不是无条件服从。

### 6.2 建议（Suggestions）：代写"你下一句"

每轮回复后给 2–4 个推进方向，每个含：

`label`（4–10 字）/ `direction`（写作意图）/ `suggestion`（**可直接发送的成品台词**）/
`anchor_speaker` + **`anchor_quote`（从该角色原话连续摘录 4–20 字，不得改写）**

`anchor_quote` 是**事实校验字段**：用来确认这个选项确实承接了刚才发生的事，而不是模型自由发挥。
提示词还明令：已经发生过的赌约/邀请/承诺不得再作为新方向；在场者不得被建议"入场"。

### 6.3 读心（Inner thought）

回复附带角色第一人称的心里话，规则极硬：

- 只允许真实态度/欲望/怀疑/害怕/嫉妒/犹豫/隐瞒/打算；
- 一句话 8–36 字，最多 50；必须补充 `message` 没说出的**新**想法；
- **严禁**环境/动作/神态描写、第三人称心理分析、对 message 的复述；
- 没有有价值的隐藏想法时输出空串，不许用旁白凑数。

> 我们已有"读心"入口（`_readMind`），但没有这种"禁止写什么"的负面清单——这正是它读起来像"心里话"而不是"旁白"的原因。

## 7. 插件模型

契约 193 行，核心是**宿主能力注入**：插件不直接碰文件/网络/模型，全部经 `PluginHost`：

| 能力 | 用途 |
|---|---|
| `invokeSuggestion` / `invokeVariants` | 生成建议 / 2–4 个候选回复 |
| `invokeNpc` | 生成临时 NPC 并写入会话 |
| `readPluginData` / `writePluginData` | 插件私有数据（键限安全标识符，路径不得逃逸） |
| `invokeHttp` | 受 `network.access` 权限约束的 HTTP |
| `listRunPersonas` / `listOffScenePersonas` / `listSessionCharacters` | 人物清单与在场/离场状态 |
| `invokeReplyAsCharacter` | 以指定人物口吻写草稿 |
| `setSessionCharacterMuted` | 禁言/解除禁言 |
| `log` | 写插件自己的日志文件 |

**两阶段动作**是我们没有的：一次动作可以返回 `choices`，用户选中后把 `selection` 传回来再执行一次
（适合"选哪个角色""选哪种改法"这类交互）。

八个内置插件：AI 联想、静音角色、读心、**剧情骰子**、随机 NPC、代角色回复、回复变体、语气润色。
注意它们几乎都是"对话动作"——插在聊天的交互位上，而不是"给 agent 加工具"。

## 8. 蒸馏

- 产物是 **Markdown 契约**（`PROFILE.generated.md` / `RELATION_GRAPH`），不是裸 JSON。
- **分块蒸馏 + 汇总合并**：证据块逐块出"局部草稿"，最后合并去重纠偏。
- **证据分期**：start / mid / end 分别用于判断"初始底色 / 稳定互动 / 弧线收束"。
- **长度硬约束**：普通字段 ≤80 汉字、列表 ≤6 项、代表句 ≤4 条且每条 ≤40 字。
- **无证据就留空**，并明确禁止写"证据不足""未知"这类占位词和省略号。
- **说话风格要落到手感**：不许只写"冷静克制""温柔含蓄"，要提口头禅、起句、连接词、句尾、代表句。
- 性别年龄只在有稳定称谓/身份/年龄序列时写，拿不准留空。
- 前期后期明显变化时，写进 `timeline_stage` / `arc_*` / `contradiction_note`，**不强行揉成一个静态人格**。

> 我们已有：分块、增量、字段级合并、失败重试、只抽指定人物、预估。
> 缺的是：**证据分期**、**长度与占位词约束**、**"说话风格落到句子手感"的具体要求**、**前后期矛盾要显式记录**。

## 9. 工程约束（值得直接照抄的纪律）

1. **提示词双份同步**：`prompts/**` 与 `kmp/server/src/androidMain/assets/**` 内容必须一致。
2. **结构化输出与调用参数一致**：NDJSON 不能同时声明 `response_format=json_object`。
3. **日志纪律**：只记截断文本与阶段指标（TTFT、重试次数），绝不落完整提示词/原文/密钥。
4. **密钥**：只进平台安全存储，不进 manifest、日志、测试快照。
5. **路径安全**：所有 run/session 标识过 `PathSafety`，禁止拼接未验证的外部路径。
6. **幂等**：operation ID / turn ID 标识一次发送，断线重放不产生重复历史。

## 10. 对照表：松江阅 vs 造梦

| 维度 | 松江阅 | 造梦 |
|---|---|---|
| **阅读器** | ✅ EPUB/TXT、排版、划词、TTS、笔记 | ❌ 没有 |
| 人物模型 | 扁平卡（性格/背景/动机/外貌） | **8 层 bundle + 写策略** |
| 会话状态 | 玩法 stats/memberStats + log | **7 块 canonical state + 稳定性分级** |
| 关系 | 书级关系图 | 基线矩阵 + **本局增量**（分层） |
| 知识边界 | 仅"锁定事实" | **holders + 知识台账** |
| 原文证据 | 蒸馏时用；对话不检索 | **每轮检索 + 按角色门控** |
| 质量闭环 | 无（错了只能重生成） | **提交后审校 + 定向重写** |
| 导演 | 5 个固定动作 + 目标 | **模型生成 2–4 个 beat 方案**（含 risk/resistance/price） |
| 下一句建议 | 无 | **代写 + anchor_quote 事实校验** |
| 读心 | 有入口，规则较松 | **负面清单极硬** |
| 插件形态 | agent 工具 + 钩子 | **聊天动作 + 两阶段选择** |
| 玩法/状态机 | ✅ 分幕/暗牌/结局/玩法包 | 有 progression，无独立玩法层 |
| 本地/离线 | ✅ 全本地 | ✅ 全本地（但需模型） |

**一句话**：它把"演得像"做到了工程化，我们把"读得好 + 能离线 + 玩法可装"做到了。两边的护城河不重叠。

## 12. 不可借鉴

- **代码**：AGPL 会传染 MIT 项目。
- **提示词原文**：属于受保护的表达，只能重写不能复制。
- **内嵌 Ktor 那套架构**：我们 Flutter 直连模型更简单，没必要为了对齐而引入本地 HTTP 层。
- **Room 双存储**：我们的 sqflite + `_ensureColumn` 自愈已经够用，换存储层收益不抵风险。
